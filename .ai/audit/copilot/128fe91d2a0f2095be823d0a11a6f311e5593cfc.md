# Copilot full-program audit for `128fe91d2a0f2095be823d0a11a6f311e5593cfc`

## Executive summary

I found **three deterministic defects** in the frozen source commit:

1. **P1** — EVM SiBot can broadcast live BUY/SELL trades and then silently drop the failure if receipt/accounting/persistence fails afterward, leaving real on-chain trades untracked.
2. **P1** — EVM AUTO execution can broadcast a route and then record it as a blank-hash `REJECTED` row, destroying the reconciliation trail for an already-submitted trade.
3. **P2** — Profit and behaviour analysis treat any token with the wrapped-base **symbol** as the wrapped base, which can corrupt realised-profit evidence and downstream leader/strategy classification.

## Findings

### COPILOT-1 — P1 — EVM SiBot swallows post-broadcast live trade failures and can leave real trades untracked

**Category:** EXECUTION_STATE

**Evidence**

- `learnerbot/sibot.py:1032` (`process_leader_event`) broadcasts a live BUY through `trader.buy(...)` before later receipt/balance checks.
- `learnerbot/sibot.py:1059` (`process_leader_event`) uses `except Exception: continue`, so any post-broadcast failure disappears without persisting a position, execution row, or operator-visible failure.
- `learnerbot/sibot.py:1141` (`close_position`) broadcasts a live SELL through `trader.sell(...)` before later receipt/balance reconciliation.
- `learnerbot/sibot.py:1093` (`_handle_leader_sell`) wraps `close_position(...)` in `except Exception: pass`, so post-broadcast SELL failures are also silently discarded.

**Impact**

If a real BUY or SELL lands on-chain but receipt polling, balance reconciliation, or DB writes fail afterward, the bot can believe nothing happened. That can produce duplicate entries/exits on later signals, balance drift between chain and DB state, and misleading Telegram/operator reporting.

**Root cause**

Broad exception suppression surrounds code that runs *after* the live execution boundary.

**Bounded corrective action**

Persist a durable execution/attempt record immediately after the tx hash is known, never swallow post-broadcast exceptions, and quarantine ambiguous positions until reconciliation resolves the chain result.

**Required tests**

- Simulate `trader.buy()` returning a tx hash and then failing during receipt or token-delta reconciliation; verify the tx hash is preserved and the position becomes pending/reconcile instead of disappearing.
- Simulate a live SELL that broadcasts and then fails during receipt/accounting; verify the position is not silently left OPEN with no recorded pending state.

**Confidence:** 0.98  
**Deterministic evidence:** yes

### COPILOT-2 — P1 — AUTO EVM execution records post-broadcast failures as blank-hash REJECTED rows

**Category:** ACCOUNTING_AND_REPORTING

**Evidence**

- `learnerbot/auto_trader.py:198` (`execute_best_live_opportunity`) calls `trader.execute_cycle(...)` and stores the broadcast tx hash in `txh`.
- `learnerbot/auto_trader.py:200` then waits for a receipt and performs realised-P&L accounting that can still fail after the trade is already submitted.
- `learnerbot/auto_trader.py:219` records the failure path with `tx_hash=""` and `status="REJECTED"`, erasing the already-known transaction identifier.

**Impact**

An already-broadcast AUTO route can be reported as if it never happened. That breaks reconciliation, misleads operators, and makes duplicate submission of the same opportunity materially more likely.

**Root cause**

The error path discards the tx hash once the code crosses from “pre-broadcast” into “post-broadcast” failure handling.

**Bounded corrective action**

Preserve the tx hash in every post-broadcast failure path and log a distinct reconciliation status such as `BROADCAST_PENDING`, `RECEIPT_TIMEOUT`, or similar instead of blank-hash `REJECTED`.

**Required tests**

- Force `execute_cycle()` to return a tx hash and `wait_for_transaction_receipt()` to time out; verify the execution log keeps the tx hash and uses a non-retry reconciliation status.
- Force an after-broadcast accounting failure and verify the tx hash still survives in the execution log.

**Confidence:** 0.99  
**Deterministic evidence:** yes

### COPILOT-3 — P2 — Wrapped-base detection trusts token symbols instead of the configured wrapped-base address

**Category:** PROFIT_CLASSIFICATION

**Evidence**

- `learnerbot/profit.py:65` and `learnerbot/profit.py:93` (`analyse_tx`) decide whether transfers are wrapped-base flows by comparing token **symbols** to `settings.wrapped_base_symbol`.
- `learnerbot/behaviour.py:129` (`classify_evidence`) removes the wrapped asset from route symbols using the same symbol-only assumption.

**Impact**

Token symbols are not unique on EVM chains. A spoofed or unrelated token that shares the wrapped-base symbol can be treated as wrapped native flow, corrupting `profit_evidence`, proof quality, behaviour labels, and downstream copy/strategy rankings.

**Root cause**

Accounting/classification logic uses mutable metadata (`symbol`) instead of the configured canonical wrapped-base token address.

**Bounded corrective action**

Use the wrapped-base address for all base-asset identification and keep symbols display-only.

**Required tests**

- Add a regression test where a non-base token uses symbol `WBNB`/`WETH` and verify it is **not** classified as wrapped-base profit evidence.
- Add a behaviour test showing a same-symbol non-base token is not stripped from route analysis as if it were the wrapped base.

**Confidence:** 0.95  
**Deterministic evidence:** yes
