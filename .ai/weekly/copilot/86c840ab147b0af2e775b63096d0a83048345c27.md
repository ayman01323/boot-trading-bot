## Findings

### CPL-001 — P0 — execution — `transfer_native` omits `'to'` field from transaction

**File:** `learnerbot/live_executor.py:707-717`

```python
tx = self._base_tx(value=int(amount * Decimal(10**18)))
try:
    gas = int(self.w3.eth.estimate_gas(tx))
except Exception:
    gas = 21000
tx["gas"] = max(21000, int(gas * 1.10))
txh = self._sign_send(tx)
```

`_base_tx()` (lines 299–308) builds a dict with `from`, `nonce`, `chainId`, `value` — but no `to`. The resolved checksum address (local variable `to`) is validated at line 703 and then never inserted into `tx`. The transaction is therefore submitted as a contract-creation call with `value` set, which wastes gas and sends native funds to the zero address.

**Impact:** All native-asset fee payouts via SiBot `close_position` and all Telegram `/send` commands silently lose funds instead of reaching the target address.

**Root cause:** Missing `tx["to"] = to` assignment between `_base_tx()` and `estimate_gas()`.

**Corrective action:** Insert `tx["to"] = to` immediately after the `_base_tx()` call. Add a post-broadcast assertion that `tx.get("to")` is non-empty before signing.

**Tests required:** Unit test that the built transaction dict includes a non-empty `to` field; integration test that simulated fee payout reaches `master_wallet` on a test RPC.

**Confidence:** 0.99 | **Deterministic:** true

### CPL-002 — P1 — billing — Activation granted on fee broadcast, not confirmed receipt

**File:** `learnerbot/fee_engine.py:63-65`

```python
def mark_activation_paid(csv_dir, telegram_id, plan_id, chain_id, amount, master, tx_hash):
    activate_user(csv_dir, telegram_id, plan_id, 'Activated by fixed on-chain fee')
    ledger(csv_dir, {..., 'status': 'BROADCAST', ...})
```

`activate_user()` is called immediately after a fee transaction is broadcast with no on-chain confirmation. A dropped or reverted payment leaves the account permanently active.

**Impact:** A user can obtain ACTIVE status by broadcasting any transaction (including one that reverts) to the activation address. Legitimate activation fee revenue may never arrive on-chain.

**Root cause:** State transition (activate_user) is performed synchronously at broadcast time. No step waits for or verifies the confirmed receipt.

**Corrective action:** Return PENDING status; add a background worker that verifies `receipt.status == 1` and `value >= expected_amount` before calling `activate_user`.

**Tests required:** Unit test: activation-fee tx that reverts must leave user INACTIVE; unit test: only a confirmed receipt with the correct value triggers activation.

**Confidence:** 0.98 | **Deterministic:** true

### CPL-003 — P1 — concurrency — TOCTOU race: `max_positions_per_chain` check not atomic with INSERT

**File:** `learnerbot/sibot.py:1010-1013`

```python
with closing(connect(app)) as conn:
    open_count = conn.execute(
        "SELECT COUNT(*) n FROM positions WHERE telegram_id=? AND chain_id=? AND status='OPEN'",
        (tid, chain.chain_id)
    ).fetchone()["n"]
if int(open_count) >= _int(cfg.get("max_positions_per_chain"), 5):
    continue
```

The count SELECT executes outside `_DB_LOCK`. `_insert_position` acquires the lock only at write time. Two concurrent BUY signals can both pass the limit check and both insert a new position.

**Impact:** `max_positions_per_chain` (default 5) can be exceeded, increasing capital exposure beyond the configured limit.

**Root cause:** Time-of-check / time-of-use (TOCTOU) — the count and the write are not in the same critical section.

**Corrective action:** Move the `open_count` SELECT inside `_DB_LOCK` and re-check after acquiring the lock before calling `_insert_position`.

**Tests required:** Concurrent `process_leader_event` calls for the same `telegram_id + chain_id` must never produce more open positions than `max_positions_per_chain`.

**Confidence:** 0.95 | **Deterministic:** true

### CPL-004 — P1 — execution — LIVE BUY broadcast with no orphan guard: position not recorded if receipt times out

**File:** `learnerbot/sibot.py:1028-1059`

```python
result = trader.buy(event['token'], amount, 'CONFIRM')
receipt = trader.w3.eth.wait_for_transaction_receipt(result['tx_hash'], timeout=180, poll_latency=2)
...
except Exception:
    continue
```

If `wait_for_transaction_receipt` times out or raises a network error after the BUY has been broadcast, the outer `except Exception: continue` fires. No position row is recorded but the user's wallet balance has already decreased. The bot has no record of the open position and will never attempt an exit.

**Impact:** Under RPC instability (common on public endpoints) a LIVE BUY can orphan user funds with zero visibility.

**Root cause:** The try/except wraps both broadcast and receipt wait in one block. Failure in the receipt-wait path discards the live transaction without a position record or user alert.

**Corrective action:** Separate broadcast from receipt wait. Persist a PENDING position row immediately after `trader.buy()` returns a `tx_hash`. Promote to OPEN (or FAILED) after receipt confirmation. Send a Telegram alert on timeout.

**Tests required:** Simulate receipt timeout after broadcast; verify a PENDING position row is created and an alert is sent.

**Confidence:** 0.97 | **Deterministic:** true

### CPL-005 — P1 — execution — LIVE SELL triggered by leader exit silently swallowed on failure

**File:** `learnerbot/sibot.py:1090-1094`

```python
try:
    close_position(app, p['position_id'], fraction, reason)
except Exception:
    pass
```

If the LIVE SELL broadcast fails (RPC error, allowance issue, gas estimation failure), the exception is discarded. The position remains OPEN, no exit is scheduled, no user alert is sent, and no circuit-breaker fires.

**Impact:** A LIVE position can stay OPEN indefinitely after a failed leader-signal exit if the leader never re-triggers the same token.

**Root cause:** `close_position` exceptions are completely swallowed in `_handle_leader_sell`.

**Corrective action:** Catch close_position exceptions explicitly, set `leader_exit_pending=1` on the position, and send a Telegram alert with the failure reason and position id.

**Tests required:** Unit test where `close_position` raises `LiveTradingError`: verify `leader_exit_pending` is set to 1 and a notification is dispatched.

**Confidence:** 0.97 | **Deterministic:** true

### CPL-006 — P1 — accounting — `profit.py` wrapped-base detection trusts token symbol, not address

**File:** `learnerbot/profit.py:65-69`

```python
symbol = tr['symbol'] or token[:10]
...
if symbol.upper() == settings.wrapped_base_symbol.upper():
    if frm in cluster and to not in cluster:
        wrapped_out = True
```

Any token contract that returns a symbol matching `WBNB`, `WETH`, or `WMATIC` is classified as the wrapped base asset and can produce `PROVEN_WRAPPED_BASE` classification.

**Impact:** A honey-pot or attacker-controlled token with a spoofed symbol is treated as the base asset, producing inflated profit evidence. A malicious wallet carrying such tokens can appear highly profitable and become eligible for SiMo leader status.

**Root cause:** The proof-quality logic keys off the metadata symbol string instead of comparing the token address to `chain.wrapped_base_address`.

**Corrective action:** Replace `symbol.upper() == settings.wrapped_base_symbol.upper()` with `token.lower() == settings.wrapped_base_address.lower()`. The address is already present in `ChainSettings`.

**Tests required:** Unit test: `analyse_tx` with a fake-WBNB token address must not produce `proof_quality=PROVEN_WRAPPED_BASE`; unit test: canonical WBNB address must produce `PROVEN_WRAPPED_BASE`.

**Confidence:** 0.97 | **Deterministic:** true

### CPL-007 — P2 — execution — `monitor_positions` stop-loss/take-profit close failure silently ignored

**File:** `learnerbot/sibot.py:1231-1235`

```python
if reason:
    try:
        close_position(app, p['position_id'], Decimal(1), reason)
    except Exception:
        pass
```

A STOP_LOSS or TAKE_PROFIT trigger that fails is silently discarded. The trigger re-fires every monitor cycle (default 10 s) but no alert is sent to the user.

**Impact:** Under sustained RPC failure a stop-loss may fail for many minutes without the user knowing. A LIVE position is exposed to continued adverse price movement during the failure window.

**Root cause:** Same bare `except/pass` pattern as CPL-005 at a different call site.

**Corrective action:** Log and send a Telegram alert with the failure reason. Optionally increment a per-position failure counter and alert the user if the stop-loss has failed N consecutive times.

**Tests required:** Unit test where `close_position` raises on a STOP_LOSS trigger: verify a Telegram alert is dispatched.

**Confidence:** 0.95 | **Deterministic:** true

### CPL-008 — P2 — safety — Solana post-execution economic validation is CSV-configurable and can be disabled

**File:** `learnerbot/solana_live_executor.py:184-199`

```python
require_output = _sol._bool(cfg.get('live_require_execute_output'), True)
require_events = _sol._bool(cfg.get('live_require_swap_events'), True)
...
if require_output and output_result <= 0:
    problems.append('non-positive executed output')
```

Setting `live_require_execute_output=false` or `live_require_swap_events=false` in the Solana settings CSV disables the checks that verify a swap produced non-zero output. A misconfigured or compromised CSV allows `swap()` to return success with zero actual tokens received.

**Impact:** Downstream callers create a position with zero actual token balance; the bot will never recover the position value.

**Root cause:** Safety-critical invariants are gated behind a runtime CSV flag instead of being unconditional.

**Corrective action:** Hardcode both checks to `True`, removing the CSV config lookup entirely.

**Tests required:** Unit test: `swap()` raises `SolanaLivePostExecutionError` when `outputAmountResult=0`, regardless of any config value.

**Confidence:** 0.93 | **Deterministic:** true

### CPL-009 — P2 — accounting — `etherscan.py cache_wallet()` fetches only page 1, silently truncating >10 000 tx wallets

**File:** `learnerbot/etherscan.py:13-37`

```python
params = {
    ...
    'page': 1,
    'offset': 10000,
    ...
}
```

`cache_wallet()` calls `_get()` which always requests page 1. For wallets with more than 10 000 transactions, older entries are silently absent from the cache. The sibot.py history path correctly implements pagination via `_fetch_action()`, but the standalone `EtherscanV2.cache_wallet()` path does not.

**Impact:** Incomplete transaction history causes incorrect cost-basis and P&L reconstruction for high-frequency wallets used by external scripts (`scripts/export_all_user_transactions.py`).

**Root cause:** No pagination loop in `EtherscanV2._get()`.

**Corrective action:** Add a pagination loop that iterates pages until fewer than `offset` rows are returned or results fall below the cutoff timestamp.

**Tests required:** Unit test with a mock returning 10 000 rows on page 1 and 5 rows on page 2: verify both pages are collected.

**Confidence:** 0.98 | **Deterministic:** true

### CPL-010 — P2 — strategy-lab — `portfolio_report()` writes new decision rows on every invocation

**File:** `learnerbot/strategy_lab.py:465-481`

```python
for row in rows:
    decision = evaluate_strategy(app, row['strategy_id'], mode=mode)
    ...
# Inside evaluate_strategy():
conn.execute(
    "INSERT INTO strategy_lab_decisions(...) VALUES(...)",
    ...
)
conn.commit()
```

`portfolio_report()` calls `evaluate_strategy()` which inserts a new `strategy_lab_decisions` row for every registered strategy on every call. The table grows unboundedly and the audit trail is polluted with repeated spurious decisions at report-view time.

**Impact:** Strategy decision history is corrupted by read operations. Automated reports called from Telegram or CI accumulate unbounded DB rows over time.

**Root cause:** Read and write paths are not separated. The reporting function calls a state-mutating evaluator.

**Corrective action:** Add a read-only reporting variant that loads the latest decision row without inserting. Gate new decision inserts behind an explicit refresh/evaluate action.

**Tests required:** Unit test: calling `portfolio_report()` twice without new shadow data must not change the row count in `strategy_lab_decisions`.

**Confidence:** 0.97 | **Deterministic:** true

### CPL-011 — P3 — accounting — `receipts.py ingest_receipt` over-counts inserted transfers on re-scan

**File:** `learnerbot/receipts.py:44-56`

```python
conn.execute(
    "INSERT OR IGNORE INTO token_transfers(...) VALUES(...)",
    ...
)
...
inserted += 1
```

The counter is incremented unconditionally even when `INSERT OR IGNORE` silently ignores a duplicate row. Re-ingesting the same receipt returns a positive `inserted` count.

**Impact:** Callers that use the return value to decide whether to re-scan see a false positive. Audit logs over-report ingest activity, making it harder to detect genuine re-processing.

**Root cause:** No check of `cursor.rowcount` or `conn.total_changes` before incrementing the counter.

**Corrective action:** Track `conn.total_changes` before and after each `INSERT OR IGNORE` and only increment `inserted` if changes increased.

**Tests required:** Unit test: ingest same receipt twice; second call must return `inserted=0`.

**Confidence:** 0.99 | **Deterministic:** true
